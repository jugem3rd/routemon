# 一括ロールバック GUI 詳細設計 (#120)

Status: Approved — implementation guide
Scope: Community WebGUI

関連:

- Issue #120、まとめIssue #94
- `docs/core/config-bulk-rollback-design.md`(Batchの状態モデルと回復範囲の正本)
- `docs/core/config-restore-design.md`(#62 単体Applyのモデル。適用 / 保存 / 再起動の3操作、状態は未保存 / 保存済み)

この文書は画面の要件を定める。**レイアウト・文言・視覚表現の具体は実装者が決めてよい。**
「何を伝えなければならないか」と「やってはいけないこと」を守ること。

## 1. 画面の位置

Sidebarへ`一括適用`を追加し、hash route `#/bulk-applies` で開く。Adminのみに表示する。

Batchの詳細は `#/bulk-applies/<batchId>` で開く。

## 2. 操作の全体像

```text
[1] 対象を選ぶ            checkpointから / Deviceと世代を個別に
        ↓
[2] 準備(読み取りのみ)     全対象のCONFIGを取得して差分を計算
        ↓
[3] 計画を確認            全台ぶんを1画面。ここで対象から外せる
        ↓  確認は1回
[4] 順次実行              1台ずつ。失敗したら止まる
        ↓
[5] 結果                  完了、または停止時の3群表示
```

## 3. 画面ごとの要件

### 3.1 対象選択

- checkpoint 一覧から選ぶ方法と、Deviceと世代を個別に選ぶ方法の両方を用意する
- checkpointは全itemが`captured`のものだけ選択できる。選べないcheckpointは理由を示す
- 適用順を利用者が決められること。既定の順序があってよい
- 共通の保存方針(`保存しない` 既定 / `すぐ保存する`)をここで1回だけ選ぶ
- 確認モード(`事前一括確認` 既定 / `Deviceごとに確認`)を選ぶ
- 最大50台

### 3.2 準備中

- 読み取りのみで、Routerの設定を変更しないことが分かる表示にする
- 進捗(n / total)を出す
- 準備は途中で中止できる

### 3.3 計画の確認(このIssueの中心)

**全対象を1画面に表示する。**Deviceごとに最低限これを出す。

| 項目 | 備考 |
|---|---|
| Device名 | |
| 適用順 | 並びで示してもよい |
| 適用する世代と取得日時 | |
| 差分の行数 | `+N行 / -N行` |
| 差分の中身を見る手段 | 展開でもリンクでもよい |
| model / Firmware / 行数 / byte size の検証結果 | |
| 高リスク差分の警告 | WAN / PPPoE / フィルタ / Supervisor自動起動行に差分がある場合 |
| 差分なしの明示 | 実行対象から外す操作を用意する |

- **確認は1回**(事前一括確認モード)。全体を確認するチェックと実行ボタン
- `Deviceごとに確認`モードでも、この計画画面は同じく全台分を見せる。実行中に各Deviceの確認を挟む
- 準備に失敗したitemや検証NGが1件でもある場合、**実行に進めない**。対象を見直す導線を出す

### 3.4 実行中

- 全体の進捗(n / total)と、成功 / 未適用 / 結果未確認の件数
- Deviceごとに現在の状態を出す。状態は`config-bulk-rollback-design.md` 3.1 のitem状態に対応させる
- いま何をしているかが分かること(準備 / 直前検査 / 確認待ち / 適用中 / 保存待ち)
- Adminが停止できる。停止を押した場合、実行中の子Applyが終端化するまで`stopping`であることを示す

### 3.5 完了・停止後

**次の3群を判別できること。** これを混ぜてはいけない。

| 群 | 意味 |
|---|---|
| 適用確認済み | `apply_verify`がtargetと一致した。保存方針に応じて未保存 / 保存確認済み / 保存失敗 / 保存未確認を併記 |
| 未適用 | 未開始、対象外、または`load`開始前に停止した |
| **適用結果未確認** | `load`開始後に失敗・切断・Server再起動・検証不能。**Router側で設定が変わっている可能性がある** |

- 停止理由を出す
- 3群それぞれのDevice一覧を出す

## 4. 回復範囲の明示(必須)

計画確認の画面と、停止後の画面に、次の趣旨を必ず出す。

- **WAN / PPPoE を壊す変更をすると、Serverから一切届かなくなる。**この機能では戻せない
- その場合の復旧はRouterの再起動または現地対応になる
- この機能が効くのは「`save`まで通って確定した後に不具合へ気付いた」場合である

文言は実装者が決めてよい。**「戻せない条件がある」ことが利用者に伝わること**が要件である。

## 5. 単体Applyが拒否されたときの表示

Batch実行中にDevice詳細から単体Applyを試みると、Serverは `code = config_apply_batch_active` と `batch_id` を含む409を返す。

- Device画面に「一括適用が実行中です」と理由を表示し、**そのBatchの詳細へリンクする**
- 単体Applyの一般的なエラーとして表示しない

## 6. やってはいけないこと

- **再試行ボタンを出さない。**失敗したBatchの自動再開・部分再開を提示しない
- **自動継続しない。**失敗後に残りを続ける導線を作らない
- 適用済みDeviceを自動で元に戻す操作を提示しない
- `apply_verify`の一致を確認する前に「成功」と表示しない
- `save`コマンドの成功応答だけで「保存確認済み」と表示しない(CONFIG_SAVED SYSLOGの受信が根拠)
- ViewerにBatch操作・計画・差分を表示しない

## 7. 実装の制約

- **依存を追加しない。**`packages/web/src/ui.tsx`の既存部品と`styles.css`のdesign tokenだけを使う
- GUI側で独自の状態機械を作らない。Server APIが返す状態をそのまま反映する
- 既存のDevice詳細・Settings・Topologyの作りに合わせる
- 横幅が狭い場合に横スクロールできること。ページ本体を横スクロールさせない
- keyboardで操作でき、状態を色だけで区別しない

## 8. 合格条件

- 準備 → 確認1回 → 順次実行 の流れが画面から追える
- 計画画面に全対象が1画面で出て、対象から外せる
- 停止時に3群が区別できる。特に「適用結果未確認」を「未適用」と混ぜない
- 遠隔から戻せない条件が画面に出ている
- 単体Apply拒否の理由とBatchへの導線が出る
- Viewerに操作が見えない
- 依存を追加していない
